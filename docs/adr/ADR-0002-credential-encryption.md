# ADR-0002：凭证加密方案

- **状态**：Accepted（用户 2026-10-16 确认，含下方"用户原话选项"）
- **日期**：2026-10-16
- **决策人**：用户（批准）/ AI 工程师（起草）
- **依据**：`DESIGN.md` P0-07「凭证加密（AES-256-GCM，密钥文件管理）」、第六章「安全相关代码必须人工确认」

---

## 1. 背景

P0-07 要求：凭证用 **AES-256-GCM** 加密、**密钥文件管理**，且**禁止硬编码密钥、禁止 ECB 模式**。

安全代码属第六章的人工检查点，故方案先经用户确认后才实施。用户选定的方案原文：

> 密钥文件用版本化 JSON，无口令保护（推荐）
> 位置 `%APPDATA%\dp_Gmail\key.json`，内容 `{version, algorithm, key(base64), created_at}`；文件权限仅当前用户可读。不需新增依赖（aes-gcm / rand / base64 均已在基线）。启动即用，无交互。

---

## 2. 决策

### 2.1 算法

**AES-256-GCM**（`aes-gcm` 0.11，`Aes256Gcm`）。

- GCM 是 AEAD：加密同时产出认证标签，密文被改动一个 bit 即解密失败。
- **不用 ECB**（`DESIGN.md` 明令禁止，且 ECB 无认证、泄露明文结构）。
- 开启 `aes-gcm` 的 `zeroize` feature，让内部密钥材料用后清零。

### 2.2 密钥文件

| 项 | 决定 |
| --- | --- |
| 路径 | `%APPDATA%\dp_Gmail\key.json`（`app.path().app_data_dir()` 下，与 `dp_gmail.sqlite` 同目录） |
| 格式 | 版本化 JSON |
| 密钥 | 32 字节随机，base64 编码后存入 |
| 口令保护 | **无** |
| 权限 | Windows：`%APPDATA%` 本就仅当前用户可访问；类 Unix：显式 `chmod 0600` |

文件形如：

```json
{
  "version": 1,
  "algorithm": "AES-256-GCM",
  "key": "<base64 的 32 字节>",
  "created_at": 1760000000
}
```

**版本或算法不匹配一律报错，不猜测、不静默降级。** 用错密钥静默解出垃圾数据，比直接失败危险得多。

### 2.3 密文布局

```
nonce(12 字节) || ciphertext || GCM tag(16 字节)
```

- nonce 每次加密由 `Nonce::generate()` 独立生成，**绝不复用**。GCM 下 nonce 复用会直接瓦解保密性。
- tag 由 `aes-gcm` 自动追加在密文尾部。
- 因此密文最小长度为 12 + 16 = 28 字节；短于此长度直接返回 `CiphertextTooShort`。

### 2.4 密钥不得进日志

密钥与明文凭证**不得**被 `tracing` 记录，**不得**出现在 `Debug` 输出里。
`SecurityError` 的各变体只携带描述字符串，不携带密钥或明文。

---

## 3. 威胁模型（明确说清能防什么、不能防什么）

| 场景 | 能否防住 |
| --- | --- |
| `dp_gmail.sqlite` 被单独拷走 | ✅ 只能拿到密文 |
| `key.json` 被单独拷走 | ✅ 只能拿到密钥，拿不到凭证 |
| 两个文件都被拷走 | ❌ 可直接解密 —— 这是无口令方案的固有上限 |
| 其他用户账户读取 | ✅ `%APPDATA%` 的 ACL + 类 Unix `0600` |
| 本机已被完全攻破（恶意进程以当前用户身份运行） | ❌ 无法防住 |
| 磁盘取证（已删除文件残留） | ⚠️ 不覆盖，属后续议题 |

**结论**：本方案的目标是"防止凭证以明文形式躺在数据库或配置里"，不是"抵御本机沦陷"。
若需要更高强度，升级路径是 2.5 的口令派生方案。

---

## 4. 后果

- 应用**启动即用，无口令交互**。
- 密钥文件丢失 = 所有已存凭证不可恢复，需重新输入。这是可接受的取舍（凭证可从邮箱服务商重新生成）。
- 密钥文件**必须**列入 `.gitignore`（已加 `*.key` / `keyfile.json`；`key.json` 追加在案）。

---

## 5. 未采纳的方案

| 方案 | 未采纳理由 |
| --- | --- |
| 裸二进制密钥文件（4 字节 magic + 1 字节版本 + 32 字节密钥） | 更精简，但无法人工查看、无法平滑轮换。用户选了 JSON。 |
| 口令派生（argon2id） | 安全性最高，但需把 `argon2` 加回依赖基线，且每次启动都要输口令。用户未选。 |
| OS 凭据库（`keyring`） | `DESIGN.md` P0-07 原文是"密钥**文件**管理"，不是 OS 凭据库。二者是不同方案，按原文取文件方案。 |
| rustls 生态的加密方案 | 与 TLS 选型无关；凭证加密只需 AEAD，不涉及证书链。 |

---

## 6. 变更流程

改动密钥文件格式（`version` 递增）、更换算法、或引入口令保护，均需：

1. 用户确认；
2. 新开 ADR 或修订本文件；
3. 提供旧格式 → 新格式的迁移路径（不得让用户已存凭证失效后无提示）。

---

## 7. 待定事项

**密文存到哪里？** 本 ADR 只定"怎么加密"，未定"密文写在哪"。

`DESIGN.md` P0-03 的表清单是 `accounts / folders / messages / attachments`，**没有凭证列也没有凭证表**。
把密文加进 `accounts`（如 `secret_encrypted BLOB`）属于**变更数据库表结构**，按第六章同样需人工确认。

**此项已提交用户，未获答复前不改动 schema。**
