## 1. 主题切换：白天 / 黑夜模式

**诉求**：现在只有一种配色，夜里太亮。需要能在设置里切换明/暗。

| 项 | 评估 |
| --- | --- |
| 新增依赖 | **不需要**（CSS 变量 + 现有 Zustand） |
| 改动范围 | `src/styles`（颜色抽成变量）+ 新增 `stores/theme.ts` + 一个开关 UI |
| 持久化 | `localStorage` 存主题标识 —— **不是密码，符合规范** |
| 风险 | 低。纯展示层 |
| 规模 | 小（半天内） |

**建议先做这一项**：投入最小、用户立刻能看见效果、不牵动任何其他模块。

## 2. 多语言：中文 / 日语 / 英语

**诉求**：现在只有中文，需要能切换语言。

| 项 | 评估 |
| --- | --- |
| 新增依赖 | **不需要**（一个字典对象 + 现有 Zustand + 一个 `t()` 函数） |
| 改动范围 | **跨切面**：约 15 个组件里的所有用户可见字符串都要抽出来 |
| **隐藏成本** | **Rust 侧的错误消息也是用户可见的**，且现在是硬编码中文（`commands/` 返回的 `String`）。要做到真正多语言，这些也得改 —— 那会动 `commands/` 的返回契约 |
| 风险 | 中。漏抽一处就出现中英混排；Rust 错误不改的话，出错时仍是中文 |
| 规模 | 大。建议分两步：先做前端 UI 字符串，再决定 Rust 错误消息怎么办 |

**必须先定一件事**：Rust 侧错误消息要不要一起多语言？
- 要 → 需要改 `commands/` 返回结构（比如返回 `{code, params}` 而不是成品字符串），
  这是**接口签名变更**，且影响所有 9 个命令。
- 不要 → 前端多语言了，但报错仍是中文。这是个**半成品**，需要用户知情。

## 3. 编译成手机版

**诉求**：要能在手机上跑。

**这是四项里唯一的大工程，且有硬性物理限制。**

### 3.1 平台可行性

| 平台 | 在**这台 Windows 机器**上能否做 | 说明 |
| --- | --- | --- |
| **Android** | 🟨 技术上可行 | 需安装 Android SDK + NDK + JDK，并执行 `tauri android init`。安装量大，且本机未验证过 |
| **iOS** | ⛔ **不可能** | 编译 iOS 必须有 **macOS + Xcode**。Windows 上无论装什么都不行 |

### 3.2 不只是「加个构建目标」

| 障碍 | 说明 |
| --- | --- |
| **数据目录** | 现在用 `%APPDATA%\com.dpgmail.desktop`。移动端沙箱路径完全不同，`DP_*` 路径逻辑要重写 |
| **密钥文件** | `key.json` 现在落在应用数据目录。移动端要考虑是否能放系统钥匙串 |
| **界面布局** | 现在是**三栏**（侧栏 + 列表 + 详情）。手机屏幕放不下，需要重做成「列表 → 点进详情」的单栏导航 |
| **`bundled` SQLite** | 需要 NDK 交叉编译，本机未验证 |
| **OAuth / 系统浏览器** | 若后续做 P3-02，移动端的回环回调机制与桌面不同 |

### 3.3 结论

**这不是「编译一下」的事，是一次平台移植。** 而且它超出了 `DESIGN.md` 里
「本地优先跨平台**桌面**邮件客户端」的既定范围 —— 按 `AGENTS.md`「授权例外」第 2 条，
属于超出锁定范围的重大事项，**必须由用户明确决定是否纳入本项目**，并新开 ADR。

建议：先做桌面端的 1 和 2，手机版单独作为一个阶段排期。

## 4. 打开时先弹 CMD 窗口 —— **已诊断，不是 bug**

**现象**：双击程序后先出现一个黑色命令行窗口，然后才是主界面。

**原因**：用户运行的是 **debug 构建**。`main.rs` 里这段是对的：

```rust
#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]
```

但它**只在 release 构建生效**。PE 头实测：

| 文件 | Subsystem | 是否弹控制台 |
| --- | --- | --- |
| `target\debug\dp-gmail.exe` | 3 = `WINDOWS_CUI` | **是** |
| `target\x86_64-pc-windows-msvc\release\dp-gmail.exe` | 2 = `WINDOWS_GUI` | 否 |

**处理**：不需要改代码。给用户一个当前代码的 release 产物即可。
（旧的那个 release 是几轮前的，缺分页、企业邮箱、新浪条目等改动，已重新构建。）

## 7. 邮件正文翻译 —— ⛔ **用户已撤回（2026-10-17）**

> **用户原话：「说错了，那先不做翻译了」。本项不做。**
> 下面保留当时记录的分析，仅供日后若重新提出时参考，**不得据此开工**。

**诉求（已撤回）**：打开一封语言与用户所选语言不同的邮件时，**自动弹提示**
「是否将这封邮件由 X 语言翻译成 Y 语言」；翻译服务商可在设置里选（百度 / 谷歌）；
国内用百度、国外用谷歌。

### 7.1 三项硬阻塞（当时记录，供日后参考）

| # | 阻塞 | 说明 |
| --- | --- | --- |
| 1 | **需要 API 密钥** | 百度翻译开放平台要 appid + 密钥；Google Cloud Translation 要开通计费项目 + API key。**这两样只能由账号持有人去注册**，我做不到 |
| 2 | **需要新增 HTTP 客户端依赖** | `Cargo.toml` 目前**没有任何 HTTP 客户端**。翻译必然要发 HTTPS 请求 ⇒ 新依赖 ⇒ 按 `AGENTS.md` 须用户批准 |
| 3 | **隐私：邮件正文会发给第三方** | 这是最要紧的一条，见 §7.2 |

### 7.2 隐私冲突：这条与「本地优先」直接矛盾

项目定位是**本地优先**的桌面邮件客户端 —— 邮件正文一直只存在于本机
（加密凭证、本地 SQLite、不联网的渲染）。

而翻译**必须把正文发给百度或谷歌**。也就是说：开启翻译的那一刻，
「本地优先」这个承诺对那封邮件就失效了。

**因此若日后重启本项，必须满足三条，否则宁可不做：**

1. **默认关闭**，由用户主动在设置里开启；
2. 开启时**明确告知**「正文会发送到 XXX」；
3. **绝不自动翻译** —— 只弹提示、由用户点确认。自动翻译等于静默外发。

### 7.3 「按用户地区自动选服务商」当时建议改成手动

判定地区要么走 IP 地理位置（**又一次外发**，且不准确），要么让用户选。
建议手动选，仅在首次开启时按系统语言给个推荐值。

## 10. 第 2 项（UI 现代化）的真机验证记录

**用户对本项的实际限定**（三轮纠正后确定）：

> 「只有平色的情况的话，你只给他搭配一个配套的颜色就行了，加个小的高光就够了，其他的不用加了。」

因此**只做了**：中栏 / 右栏各给一层与当前主题配套的半透明底色 + 顶部一道 1px 高光。
**明确没做**：圆角、毛玻璃（`backdrop-filter`）、阴影投射、任何布局改动。

### 10.1 实现

```css
.app__list   { background: color-mix(in srgb, var(--surface) 52%, transparent); box-shadow: inset 0 1px 0 var(--glass-border); }
.app__detail { background: color-mix(in srgb, var(--surface) 38%, transparent); box-shadow: inset 0 1px 0 var(--glass-border); }
```

用 `color-mix` 而非写死色值：深色主题下自动得到深色配套色，不必再写一套。

### 10.2 验证（WebView2 CDP 实测，2026-10-17）

截图：`docs/verification/panel-light.png`、`panel-dark.png`

| # | 判据 | 实测 |
| --- | --- | --- |
| 1 | 中栏有底色（非 transparent） | ✅ 明 `color(srgb 1 1 1 / .52)` / 暗 `color(srgb .106 .122 .149 / .52)` |
| 2 | 右栏有底色 | ✅ 明 `/.38` / 暗 `/.38` |
| 3 | 中右两栏层次不同 | ✅ `.52` vs `.38` |
| 4 | 中栏有高光 | ✅ `rgba(255,255,255,.55) 0 1px 0 inset` |
| 5 | 右栏有高光 | ✅ 同上 |
| 6 | **没有圆角**（用户要求不加） | ✅ 两栏均 `0px` |
| 7 | **没有毛玻璃**（用户要求不加） | ✅ 两栏 `backdrop-filter: none`（侧栏有 `blur(22px)`，那是上一轮保留的） |
| 8 | 深色下底色跟着变 | ✅ 明 `srgb 1 1 1` → 暗 `srgb .106 .122 .149` |
| 9 | 深色下中右仍分层 | ✅ `.52` vs `.38` |
| 10 | 深色下仍是方角 | ✅ `0px` |

**11/11 通过。** 第 6、7 两条是**反向断言** —— 它们证明「用户说不要的确实没加」，
比正向断言更容易被忽略，故单列。

## 11. 第 3 项（多语言中/日/英）的实现与验证

**决策记录见 `docs/adr/ADR-0005-frontend-i18n-backend-errors-zh.md`。**
一句话：**只做前端**，`commands/` 的返回契约不动，Rust 报错恒为中文（用户已知情接受）。

### 11.1 结构（零新增依赖）

| 文件 | 职责 |
| --- | --- |
| `src/lib/i18n/zh.ts` | **所有 key 的唯一来源**，`as const` |
| `src/lib/i18n/ja.ts` / `en.ts` | 约束成 `Record<Key, string>` ⇒ **漏译即 `tsc` 报错** |
| `src/lib/i18n/index.ts` | 语言表、`{name}` 插值、`createTranslator`（带 `locale`） |
| `src/lib/i18n/useT.ts` | `useT()` / `useFormat()`，React 侧唯一入口 |
| `src/stores/language.ts` | Zustand + `localStorage` + 跟随系统语言 |
| `src/features/settings/LanguageSelect.tsx` | 侧栏下拉框，与主题按钮并排 |

为什么不用 i18n 库：那需要新增依赖（须人工批准），而**类型系统已经能做完整性检查**。
`ja` / `en` 少一个 key 或拼错一个 key，`tsc --noEmit` 直接红，比运行时回退可靠。

### 11.2 跟随语言的另外两处

- **日期格式**：`formatDateTime(unix, locale, noDate)` 接地区码，`zh-CN` / `ja-JP` / `en-US`
  各按本地习惯输出（实测 `2026/10/17 11:42` vs `10/17/2026, 11:42 AM`）
- **`<html lang>`**：随语言写入，影响断词与字体回退（日语无空格，差别明显）

## 12. 第 4 项（多套主题 + 重点色）的实现与验证

**用户原话**：「不只明/暗两套，要能选**多套主题**，并且**重点色（accent）可自选**。」

### 12.1 两个正交维度，不是一个「20 选 1」

如果按字面把「4 套主题 × 5 种重点色」做成 20 个主题 ID，
那么词典、CSS、下拉框、持久化、测试全都要乘 5 —— 而其中**只有色相不同**。

所以拆成两个独立属性：

| 维度 | 属性 | 取值 |
| --- | --- | --- |
| 基调 | `<html data-theme>` | `light` / `dark` / `sepia` / `midnight` |
| 重点色 | `<html data-accent>` | `azure` / `emerald` / `violet` / `amber` / `rose` |

```css
/* 色相与两档明度来自 [data-accent]，饱和度/明度档位来自 [data-theme] */
--accent: hsl(var(--accent-hue) var(--accent-sat) var(--accent-light));
```

**20 种组合只写了 5 条色相 + 2 组明度档位**，不是 20 条。

### 12.2 为什么每个重点色要给两档明度

同一个绿，浅底上要用**暗绿**才压得住白字，深底上却要**亮绿**才看得清。
只给一档的话必然有一半组合不达标 —— 实测正是如此：

| 重点色 | 46% 明度 + 白字的对比度 | 处理 |
| --- | --- | --- |
| 绿 (`emerald`) | **约 2.2 : 1** ❌ | 浅底档压到 28% |
| 橙 (`amber`) | 约 3.3 : 1 ❌ | 浅底档压到 38% |
| 蓝 / 紫 / 玫红 | 4.8 / 7.8 / 5.5 ✅ | 保持 44–48% |

明度的最终取值不是审美拍的，是按下表**实测**后回填的。

## 14. 第 8 项：每 15 秒自动收信

**用户原话**：「设置一下，每 15 秒自动拉取一次邮件，防止多次手动刷新。」

### 14.1 三条自我约束

「每 15 秒」如果照字面直做，会变成自伤。所以加了三条：

| 约束 | 理由 |
| --- | --- |
| **窗口不可见时不发** | 最小化后还每 15 秒登一次 IMAP 是纯浪费，也平白增加被限流的概率 |
| **不叠加** | 上一轮没回来就跳过这一轮。网络慢时死等，否则会堆出一串并发连接 |
| **失败静默** | 每 15 秒弹一次红色报错比不报更糟。手动点「同步」仍如实报错 —— 那是用户主动发起的 |

间隔**固定 15 秒**，不做间隔选择器（多一个下拉框就多一种用户能配出问题的状态）。
但**给了开关**：每小时 240 次 IMAP 连接，服务商有可能限流，用户得能一键关掉。

### 14.2 真机验证：用**外部 TCP 观测**，不是看界面

这是本项目第一次验证「后台定时任务」，也踩了一个坑（见 §14.4）。

方法：按 300 ms 采样应用的 TCP 连接，看是否连向 IMAP 的 993 端口。

| 状态 | 采样结果 |
| --- | --- |
| **开启**（约 108 秒） | 命中 12 次，时间点换算出的**间隔：15.1 / 15.2 / 14.2 / 15.7 / 14.3 / 15.0 / 14.9 秒** |
| **关闭**（约 45 秒 = 3 个周期） | **命中 0 次** |

所以「自动收信确实在按 15 秒跑」和「开关确实能关掉它」两件都是实测的，
不是看代码推断的。远端地址 `2408:876a:1110:100:0:14:33:205`（163 的 IMAP），确认打的是真服务器。

界面侧：开关状态写进 `localStorage.dpgmail.autosync`，
侧栏出现「自动收信：每 15 秒」提示（否则用户看到邮件自己冒出来会以为是 bug）。

### 14.3 尚未验证

| 项 | 说明 |
| --- | --- |
| **服务商限流** | 每小时 240 次连接，163 在 108 秒里没报错，但**没有跑够长时间**看是否会被限流或临时封禁 |
| **「窗口最小化时暂停」未实测** | 只验过 `document.visibilityState === "visible"` 这一条分支；最小化那条分支是按规范写的，没实际最小化后观测过 |
| **「不叠加」未实测** | 需要一个慢到超过 15 秒的同步才能触发，本机网络下没构造出来 |
| **失败静默的行为** | 没有构造过「自动收信失败」的场景（需要断网或改错授权码） |
| 多账户 | 只同步**工具条里当前选中的那个账户**，不是所有账户。多账户用户要切账户才能收另一个 —— 这是有意的简化，但没跟用户确认过是否够用 |

### 14.4 踩到的坑：**改 `__TAURI_INTERNALS__.invoke` 是改不动的**

第一次想验证「自动收信有没有被调用」，做法是在 webview 里给
`window.__TAURI_INTERNALS__.invoke` 打补丁计数。结果计数**始终为 0**，
差点得出「自动收信没跑」的错误结论。

实际原因：那个属性**不可写**（sloppy mode 下赋值静默失败，不报错）。
连直接 `await window.__TAURI_INTERNALS__.invoke("list_accounts")` 都不计数 ——
说明补丁根本没生效，是**观测手段坏了**，不是被测对象坏了。

**教训：验证工具本身要先证明能测到东西。** 一个永远返回 0 的计数器
和「功能没实现」长得一模一样。改用外部 TCP 观测（进程之外、不依赖被观测代码配合）
才拿到可信数据。
