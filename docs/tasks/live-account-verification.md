> 2026-10-17。用户提供了真实 QQ 邮箱与授权码，
> 本项目**最大的一笔验证债**（「客户端从未收发过一封真实邮件」）就此结清。

---

## 1. 这一笔债此前为什么一直挂着

见 `live-network-verification.md`：那一轮用伪造凭证把**连接层**跑通了，
但邮箱层（`SELECT` / `FETCH`）、投递层（SMTP `DATA`）、
以及网易 `ID` 命令都还零执行 —— 因为它们全部位于「登录成功」之后。

判据没变：**没有真实跑通过的功能，不得只写「完成」。**
所以那句话一直挂着，直到真的收发成功。

## 2. 凭证怎么处理

**测试文件里不含任何账号或授权码。** 一律从环境变量读：

```powershell
$env:DP_GMAIL_TEST_USER   = "you@qq.com"
$env:DP_GMAIL_TEST_SECRET = "16 位授权码"
cargo test --manifest-path src-tauri/Cargo.toml --test live_account_test -- --ignored --nocapture --test-threads=1
```

三条设计约束：

| 约束 | 理由 |
| --- | --- |
| 只读环境变量，不写文件 | `DESIGN.md` 验收总则「无硬编码密码」 |
| 全部标 `#[ignore]` | CI 无凭证；但 **「N ignored」每次都会显式打印**，不是消失 |
| 缺变量时**直接失败**，不静默跳过 | 静默跳过会让「没跑」看起来像「跑过了」—— 正是本项目反复防的假阳性 |

提交后已核查：**工作区文件与提交历史中均无授权码**。

### 3.3 解析体检：`live_parse_audit`

拿 30 封真实邮件（实得 31 封）逐个检查 `from` / `subject` / `date` 是否解析得出。

**第一次运行：31 封里 3 封有缺字段。** 合成数据永远撞不出这些：

| UID | 现象 | 根因 |
| --- | --- | --- |
| 309 / 334 | `from = None` | `From` 头**没有地址**，只有 RFC2047 显示名（解码为「NOI竞赛办公室」），真实地址在 **`Sender`** 头里 |
| 316 | `date = None` | 整封邮件**没有 `Date` 头** |

### 3.4 由体检驱动的一处真实修复

`parser.rs` 新增 `resolve_from()`：`From` 里取不到地址时回退到 `Sender`，
**同时保留 `From` 的显示名**（「NOI竞赛办公室」比裸地址对用户有用）。

修完复验（同一条体检、同一批真实邮件）：

```
[体检] 检查 31 封，1 封有缺字段      ← 修之前是 3 封
```

剩下那 1 封是 UID 316 的「无 `Date` 头」。`parser.rs` 里
`date_unix.unwrap_or(0)` 是**已记录的有意选择**（排到列表末尾，不会被误当成新邮件），
不算缺陷。

单测两条守门用例（`parser_test.rs`）：

- `falls_back_to_sender_when_from_has_no_address` —— 用真实那封的头部原样构造
- `prefers_from_when_it_has_an_address` —— 防止回退把正常邮件的发件人顶掉

## 8. 应用端到端：UI → IPC → `sync_folder` → 落库 → 列表（2026-10-17 补）

**这是整条链路里最后一个没被真实数据覆盖的环节。** 此前验的都是库函数
（`fetch_recent` / `send_mail`）与存储层，唯独应用**自己**的命令编排、
Tauri 的 `State` 注入、IPC 序列化没走过。

### 8.1 前置：清掉仿真数据（用户选 B）

`%APPDATA%\...\dp_gmail.sqlite` 里原有 1260 封**仿真**数据（早期为测性能灌的）。

**先备份再删** —— `VACUUM INTO` 生成一致的单文件备份（比直接复制 `.sqlite`
安全，后者可能丢掉 `-wal` 里未合并的事务）：

```text
[备份] %APPDATA%\com.dpgmail.desktop\backup\dp_gmail_before_clean_2026-10-17T04-08-52.sqlite
[备份] 1.39 MB

[删除前] accounts 2 / folders 3 / messages 1260 / attachments 141 / messages_fts 1260
[删除后] 全部 0 ✅（密钥文件 key.json 未动）
```

删除按外键安全顺序显式执行（`attachments → messages → folders → accounts`），
不依赖 `CASCADE` —— 万一 schema 没给每条都设，显式顺序会当场暴露。

### 8.2 真实窗口里的完整操作

用 CDP 驱动**真实界面**（不是调命令），授权码经环境变量注入、不落盘：

```text
① 输入 mcpcnano@163.com  → 「已识别：网易163邮箱（imap.163.com:993）」  ← 自动识别在应用里也对
② 点「添加账户」          → 已配置账户：mcpcnano@163.com · 网易163邮箱 · 已存凭证
③ 选中该账户 + INBOX      → 点「同步」
④ 结果                    → 「拉取 5 封，写入 5 封」
⑤ 文件夹树                → mcpcnano@163.com / INBOX 5 5
⑥ 邮件列表                → 5 封真实邮件，其中「dp_Gmail 真机自检 1792208556」带 📎 1
```

第 ⑥ 行那封 `📎 1`，就是早前**真发出去、真收回来**的那封 —— 现在通过应用自己的界面显示，
连附件计数都从库里读对了。

### 8.3 落库核对（直接查 SQLite）

```text
[账户]     #3 mcpcnano@163.com | provider=netease163 | 密文长度=44
[文件夹]   INBOX
[计数]     messages 5 / messages_fts 5 / attachments 1 / 未读 5
[明文泄漏] ✅ 库中无明文授权码
```

**密文 44 字节 = 12（nonce）+ 16（明文授权码长度）+ 16（GCM tag）** ——
算术对得上，证明存的确实是加密块而不是别的什么东西。
