# P4-02 前端单元测试（**待依赖决策，未开工**）

> 2026-10-17。记录一个真实的覆盖缺口 —— 它卡在「新增依赖需人工批准」上，
> 所以本轮只做记录，不写代码。

## 1. 事实

`要求1.txt` §七「文档」里列的测试命名规范是：

```
测试         *_test.rs / *.test.tsx
```

前半（Rust）执行得很好 —— 现有 30 个测试二进制、202 条用例。
**后半从未落地。** 实测：

| 检查 | 结果 |
| --- | --- |
| `src/**/*.test.ts(x)` | **一个都没有** |
| `package.json` 里的测试框架 | **无** vitest / jest / testing-library / playwright / cypress |
| `npm run` 里的测试脚本 | **无** |

## 2. 受影响的是哪些逻辑

不是「所有前端代码都没测」——大部分是渲染，靠真实窗口实跑验证。
但有三处是**纯函数**，本该有单测：

| 文件 | 里面是什么 | 风险 |
| --- | --- | --- |
| `src/features/compose/drafts.ts` | `buildReply` / `buildForward`：拼收件人、加 `Re:` / `Fwd:` 前缀、引用原文 | **最高**。回复转发发错人是不可撤销的 |
| `src/features/inbox/listLabels.ts` | `listTitle` / `emptyHint` 的分支 | 低（纯文案） |
| `src/lib/format.ts` | 发件人/时间格式化 | 中（日期解析出错会让邮件看起来来自错误的时间） |

`buildForward` 尤其值得测：它决定**附件和原文怎么带过去**，而这一块目前
只在真实窗口里手点过 —— 我点过一次「转发」按钮，但那不等于覆盖了
「没有 `from` 的邮件转发会怎样」这类边界。

## 3. 为什么本轮没做

补前端测试要装 vitest（外加 `jsdom` 或 `happy-dom` 才能测组件）。
而 `要求.txt` 第 1 条是「**技术栈锁定，不得新增依赖**」，
`AGENTS.md` 第 1 条是「新依赖必须人工批准并写入 `docs/adr/`」。

**这不是我能在「授权例外」下自行决定的事** —— 例外第 2 条明确写着
「超出 `DESIGN.md` 已锁定范围」的重大事项仍须请示，而技术栈正是锁定的那部分。

## 4. 需要你定什么

| 选项 | 代价 | 收益 |
| --- | --- | --- |
| **A. 装 vitest**（推荐） | 新增 1–2 个 devDependency，写进 ADR-0005 | 三个纯函数模块可测；`*.test.tsx` 命名规范落地 |
| B. 只装 vitest，不装 DOM 环境 | 更少的依赖 | 只能测纯函数，测不了组件 —— **其实够用**，因为待测的三处都是纯函数 |
| C. 不装，维持现状 | 零依赖 | 上述逻辑长期靠人工点验证；`buildReply` 的边界（无收件人、无正文、超长主题）永远是盲区 |

**我倾向 B**：待测的三处全是纯函数，不需要 DOM 环境，
依赖增加最少，且直接补上「核心逻辑有单元测试」这条验收。

## 5. 边界

即便装了测试框架，也**不能**用它替代真实窗口验证 —— 现有那些
「实跑验证」记录（滚动帧率、分页、详情渲染、企业邮箱选择器）衡量的东西
单测测不出来。两者是互补，不是替换。
