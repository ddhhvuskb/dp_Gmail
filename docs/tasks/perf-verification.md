# 性能验收实测

- **对应标准**：`DESIGN.md` 验收总则「1000 封列表滚动不卡，**搜索 <200ms**」
- **状态**：✅ 后端查询耗时已实测并钉成回归测试（2026-10-16）
- **测试文件**：`src-tauri/tests/performance_test.rs`

---

## 1. 为什么单独做这件事

这条验收标准此前**只有设计上的论证，没有实测数字**。
P1-01 还专门标注过一处风险：「LIKE 回退路径走全表扫描，是唯一有性能风险的分支」。

本文件把它变成可重复、可回归的实测。

## 2. 测试方法

- 种子数据：**1000 封**邮件，分属 **2 个账户**的 INBOX，内容为中文主题 + 中文正文 + 部分带附件。
- 覆盖四条路径：FTS 检索（≥3 字符）、LIKE 回退（<3 字符）、列表查询、统一收件箱。
- 额外覆盖**深翻页**（OFFSET 950）—— OFFSET 分页的经典退化点。
- 最坏情况：单字「的」高频命中，顶到 `limit=200` 上限。

## 3. 实测结果（debug 构建）

| 路径 | 实测 | 预算 |
| --- | --- | --- |
| FTS 检索 `项目进度` | **0.63 ms** | 200 ms |
| FTS 检索 `里程碑与风险` | 1.22 ms | 200 ms |
| FTS 检索 `sender3@qq.com` | 0.90 ms | 200 ms |
| LIKE 回退 `项目` | 2.12 ms | 200 ms |
| LIKE 回退 `进度` | 1.42 ms | 200 ms |
| LIKE 回退 `发票` | 1.33 ms | 200 ms |
| **最坏情况** 单字 `的`（200 条命中） | **2.11 ms** | 200 ms |
| `list_messages(1000)` | 1.57 ms | 200 ms |
| `list_unified_messages(1000)` | 6.14 ms | 200 ms |

**全部远低于预算，最慢的一项也只有预算的 3%。**

注意这是 **debug 构建**（`cargo test` 默认），release 下会更快。
换言之，用 debug 数字对比预算已经足够，无需为跑测试专门构建 release。

## 4. 结论与边界

### 4.1 可以下的结论

- **搜索 <200ms**：在 1000 封规模下成立，且余量极大。
- 有性能风险的 LIKE 回退分支实测 **2.12 ms**，全表扫描在本地规模下不构成问题。

### 4.2 不能下的结论

- **规模外推有限**。万级、十万级邮件下 LIKE 回退是全表扫描，会线性变慢；
  FTS 路径则有索引支撑。真到那个规模需要重新测。

> 「1000 封列表滚动不卡」原来只验了一半（只量了后端查询 1.57 ms）。
> **前端滚动帧率已于 2026-10-17 补测，见 §6。**
> 补测同时发现一处**功能性缺口**：列表硬顶在 200 条且无翻页，见 §6.3。

## 5. 测试自身踩的坑

第一次运行时两条用例失败：

```
[发票] 应有命中
  的: 命中 0 条
```

**不是代码问题，是我的种子数据里压根没有「发票」和「的」这两个词。**
断言写在了不存在的数据上。

已修正种子数据，并给最坏情况用例补了一条 `assert!(!hits.is_empty())` ——
否则这条用例会在「零命中」的情况下**悄悄通过**，看起来测了最坏情况，实际什么也没测。

这正是那类「测试全绿但没测到东西」的假阳性，值得单独记一笔。

## 6. 滚动帧率实测（2026-10-17 补测）

### 6.1 方法 —— 在**真实窗口**里量，不是另建一个环境

`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 这条路**走不通**：`wry` 在
`webview2/mod.rs:333` 无条件调用 `set_additional_browser_arguments()`，
而 WebView2 的该属性一旦被显式设置，环境变量就被忽略。

可行的做法是 `tauri-build` 认 `TAURI_CONFIG` 环境变量（`lib.rs:681`，
JSON Merge Patch 语义），于是**不用改仓库里任何一个文件**：

```powershell
$env:TAURI_CONFIG = '{"app":{"windows":[{"label":"main","title":"dp_Gmail","width":1400,"height":1000,"resizable":true,"additionalBrowserArgs":"--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection --remote-debugging-port=9222"}]}}'
cargo build --manifest-path src-tauri/Cargo.toml
```

> 数组是**整体替换**不是合并，所以窗口对象必须写全。
> 构建前**必须先停掉正在运行的 exe**，否则 `os error 5 拒绝访问`。

然后用 Node 24 内置的 `fetch` + `WebSocket` 直连 CDP，在页面里跑测量脚本：

```js
// 程序化滚动整个列表，记录每帧间隔
for (let i = 1; i <= steps; i++) {
  await new Promise((r) => requestAnimationFrame(r));
  scroller.scrollTop = Math.round((max * i) / steps);
  void scroller.offsetHeight;          // 强制同步布局，把代价算进本帧
  frames.push(performance.now() - last);
}
```

**量完必须还原**：`git checkout` 两个临时常量、不带 `TAURI_CONFIG` 重新构建，
并**实测确认 9222 端口已关闭**（已验证）。

### 6.2 结果

真实数据：两个账户共 1260 封（`zhangsan@qq.com` INBOX 900 + Sent 60、
`work.li@qq.com` INBOX 300）。窗口 1400×1000，行高 64 px。

| 场景 | 列表行数 | 滚动总高度 | 挂载行数（顶/底） | DOM 节点（顶/底） | p50 | p95 | max | >16.7ms |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 张三 INBOX | 200 | 12 800 px | 24 / 24 | 225 / 226 | 7.0 ms | 10.1 ms | 12.9 ms | **0** |
| 统一收件箱（临时放宽上限） | **1200** | 76 800 px | 24 / 24 | 249 / 251 | 7.3 ms | 12.3 ms | 14.7 ms | **0** |

（p50 ≈ 7 ms 说明该显示器刷新率约 144 Hz，rAF 未被节流 —— 否则数字会接近 1000 ms，
是节流信号而不是好消息。）

**结论**：
- 从 200 行到 1200 行，帧耗几乎不变（p50 7.0 → 7.3 ms）—— 虚拟化的代价与列表长度无关，符合预期。
- 挂载行数恒定 **24**，DOM 节点数在顶部与底部只差 2 个。**全量渲染的退化没有发生。**
- 整列表 200 帧滚动**无一帧超过 16.7 ms**。在 144 Hz 显示器上还有约一倍余量。
- **「1000 封列表滚动不卡」在前端侧成立**，实测规模 1200 封 > 要求的 1000 封。

### 6.3 但补测暴露了一处功能性缺口

`impliedRowCount` 在**未放宽上限**时是 **200** —— 而那个文件夹里有 **900 封**。

| 位置 | 值 |
| --- | --- |
| `src/features/inbox/useInbox.ts:9` | `PAGE_SIZE = 200` |
| `src-tauri/src/commands/messages.rs:11` | `MAX_PAGE_SIZE = 200` |
| 翻页 / 无限滚动 | **不存在** —— `useListRows` 只请求 `offset = 0` 一页 |

**后果：一个 900 封的收件箱，用户最多只能看到最新的 200 封，另外 700 封在界面上不可达。**

这不是性能问题，是功能缺口。而且 §6.2 已经证明：**把上限放宽到 1200，界面毫无压力** ——
也就是说卡住可达性的**只有那个上限本身**，不是渲染能力。

> 判据照旧：验收标准写的是「1000 封列表滚动不卡」。
> 如果列表根本装不下 1000 封，这条标准就没有被真正满足过 —— 只是没被触发。

**根因**：200 是一个**单次请求**的安全上限（合理），
但从未配套实现分页，于是它退化成了**产品功能上限**（不合理）。

修法不是把常量调大（那只是把天花板挪高，IPC 传参会随规模爆炸），
而是按 200 一页做增量加载。
