# 性能验收实测

- **对应标准**：`DESIGN.md` 验收总则「1000 封列表滚动不卡，**搜索 <200ms**」
- **状态**：✅ 后端查询耗时已实测并钉成回归测试（2026-10-16）
- **测试文件**：`src-tauri/tests/performance_test.rs`

---

## 1. 为什么单独做这件事

这条验收标准此前**只有设计上的论证，没有实测数字**。
P1-01 还专门标注过一处风险：「LIKE 回退路径走全表扫描，是唯一有性能风险的分支」。

本文件把它变成可重复、可回归的实测。

## 2. 测试方法

- 种子数据：**1000 封**邮件，分属 **2 个账户**的 INBOX，内容为中文主题 + 中文正文 + 部分带附件。
- 覆盖四条路径：FTS 检索（≥3 字符）、LIKE 回退（<3 字符）、列表查询、统一收件箱。
- 额外覆盖**深翻页**（OFFSET 950）—— OFFSET 分页的经典退化点。
- 最坏情况：单字「的」高频命中，顶到 `limit=200` 上限。

## 3. 实测结果（debug 构建）

| 路径 | 实测 | 预算 |
| --- | --- | --- |
| FTS 检索 `项目进度` | **0.63 ms** | 200 ms |
| FTS 检索 `里程碑与风险` | 1.22 ms | 200 ms |
| FTS 检索 `sender3@qq.com` | 0.90 ms | 200 ms |
| LIKE 回退 `项目` | 2.12 ms | 200 ms |
| LIKE 回退 `进度` | 1.42 ms | 200 ms |
| LIKE 回退 `发票` | 1.33 ms | 200 ms |
| **最坏情况** 单字 `的`（200 条命中） | **2.11 ms** | 200 ms |
| `list_messages(1000)` | 1.57 ms | 200 ms |
| `list_unified_messages(1000)` | 6.14 ms | 200 ms |

**全部远低于预算，最慢的一项也只有预算的 3%。**

注意这是 **debug 构建**（`cargo test` 默认），release 下会更快。
换言之，用 debug 数字对比预算已经足够，无需为跑测试专门构建 release。

## 4. 结论与边界

### 4.1 可以下的结论

- **搜索 <200ms**：在 1000 封规模下成立，且余量极大。
- 有性能风险的 LIKE 回退分支实测 **2.12 ms**，全表扫描在本地规模下不构成问题。

### 4.2 不能下的结论

- **「1000 封列表滚动不卡」只验了一半。** 本测试量的是**后端查询耗时**（1.57 ms），
  而「滚动不卡」还取决于前端虚拟化 —— 那部分仍未用真实数据验证过。
- **规模外推有限**。万级、十万级邮件下 LIKE 回退是全表扫描，会线性变慢；
  FTS 路径则有索引支撑。真到那个规模需要重新测。

| 项 | 说明 |

| **滚动帧率** | 后端查询 1.57 ms 与「滚动不卡」是两件事。虚拟化渲染的帧率**从未测量**。 |

## 5. 测试自身踩的坑

第一次运行时两条用例失败：

```
[发票] 应有命中
  的: 命中 0 条
```

**不是代码问题，是我的种子数据里压根没有「发票」和「的」这两个词。**
断言写在了不存在的数据上。

已修正种子数据，并给最坏情况用例补了一条 `assert!(!hits.is_empty())` ——
否则这条用例会在「零命中」的情况下**悄悄通过**，看起来测了最坏情况，实际什么也没测。

这正是那类「测试全绿但没测到东西」的假阳性，值得单独记一笔。
