## 1. 方法

用 Node 24 内置的 `node:sqlite` 直接往**应用真实数据库**（`%APPDATA%\com.dpgmail.desktop\dp_gmail.sqlite`）
灌入仿真数据，再启动应用观察。

灌入量：

```
accounts     = 2      （张三（主号）900 封、李四（工作）300 封）
folders      = 3      （两个 INBOX + 一个 Sent）
messages     = 1260
attachments  = 141
messages_fts = 1260   ← 与 messages 一一对应
FTS 查「项目进度」命中 = 116
```

刻意设计的两点：
- **四分之一邮件未读**，用于验证未读样式与未读计数。
- **每封的 HTML 正文里都埋了 `<script>` 与 `<img onerror>`**，用于验证净化。

## 2. 验证结果

### 2.1 文件夹树与计数

截图左侧显示：

| 文件夹 | 未读 | 总数 |
| --- | --- | --- |
| 张三（主号）/ INBOX | **225** | **900** |
| 张三（主号）/ Sent | 15 | 60 |
| 李四（工作）/ INBOX | **75** | **300** |

900 ÷ 4 = 225、300 ÷ 4 = 75 —— **与种子数据的未读比例完全吻合**，
说明 `list_folders` 的未读统计 SQL 正确。

### 2.2 邮件列表（真实数据 + 虚拟化）

- 12 行可见邮件，发件人 / 主题 / 时间齐全。
- 时间严格倒序（01:07 → 00:44）。
- **未读行加粗、已读行常规**，与 `is_seen` 对应。
- 带附件的行显示 `📎 1` 徽标。
- 列表显示的是第 289–299 封（最新在前），与 300 封的倒序一致。

> 虚拟化本身只挂载可视区附近的十余行，故截图里看不出「1260 封」的体量 ——
> 这正是它该有的表现。**但「滚动不卡」仍未做帧率级实测**，只验证了渲染正确。

### 2.3 详情渲染 + **XSS 防护（本轮最关键的证据）**

点击一封邮件后，右侧详情面板显示：

- 标题 `Re: 关于下周评审的安排（296）`
- 发件人 `赵六 <zhaoliu@163.com>`、收件人、时间
- 正文正常渲染：段落、`<br>` 换行、中英混排都正确

**三条XSS 防护证据：**

| 埋入的攻击载荷 | 预期 | 实测 |
| --- | --- | --- |
| `<script>document.body.innerHTML = "<h1>如果看到这段，说明净化失效了</h1>"</script>` | 被整段剥除 | ✅ **页面上没有出现该文字** |
| `<img src="x" onerror="document.title='XSS'">` | 属性被剥离 | ✅ **窗口标题仍是 `dp_Gmail`**，处理器未执行 |
| `<img>` 标签本身 | 保留 | ✅ 显示为破图图标（标签在、事件属性不在） |

这证明了完整链路：`commands::get_message` → `security::sanitize_html` → 前端渲染，
**在真实应用、真实数据下确实拦住了脚本执行**。

### 2.4 FTS 触发器对外部写入同样生效

种子数据是用 **Node 进程**（不是应用）写进 `messages` 表的，
而 `messages_fts` 仍然精确等于 1260。

这证明 FTS 同步靠的是**数据库触发器**而非应用代码路径 ——
任何写入来源都会被索引，不存在"必须走某个 Rust 函数才会被搜索到"的隐藏前提。

## 4. 工程备注：UI 自动化的坑

本轮为点击界面写了几版 PowerShell 脚本，踩到三个坑，记录备查：

1. **`[ref]$rect` 在带 `param()` 块的脚本里建不出结构体** → 改用无参脚本 + 硬编码变量。
2. **窗口 `Left` 为负时坐标映射不可靠** → 先用 `MoveWindow` 把窗口挪到固定位置。
3. **`$winX + 500` 求值为空**（原因未查明）→ 最终全部改用字面量坐标。

结论：这类一次性 UI 自动化，**字面量坐标最可靠**，不要做算术。
