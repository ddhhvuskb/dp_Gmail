## 2. 核了但**不是** bug 的一处

此前会话记着「800px 窗口高度下『统一收件箱』按钮被截掉一半」。本轮用真实窗口
在**默认尺寸 1200×800** 下实测：

```json
{
  "viewport": { "w": 1200, "h": 800 },
  "sidebar": { "top": 0, "bottom": 800, "scrollHeight": 921, "clientHeight": 800,
               "overflowY": "auto", "overflowPx": 121 },
  "unifiedButton": { "top": 744, "bottom": 773, "h": 29 },
  "unifiedClippedByViewport": 0,
  "unifiedFullyVisible": true
}
```

按钮底边 773 ≤ 800，**完全可见**。侧栏内容确实比可视区高 121px，但它
`overflow-y: auto`，可滚动 —— 那是正常的响应式行为，不是缺陷。

**结论：这条旧记录不准确，不要再去「修」它。**
（当初多半是在别的窗口尺寸下看到的，被当成默认尺寸的问题记了下来。）

## 3. 本轮实际改了什么

### 3.1 补上分页的加载提示（自己上一轮引入的缺口）

`perf-verification.md` §6.5 把列表改成了按 200 一页增量加载，但**没有做任何加载提示**。
网络一慢，列表看起来就是「到头了」—— 用户不会去区分「只有这么多」和「还在取」。

- `MessageList.tsx` 新增 `isLoadingMore` 属性，为真时在列表末尾渲染「正在加载更多…」；
- `App.tsx` 传 `rows.isFetchingNextPage`。

真实窗口实测（900 封的文件夹）：

```json
{
  "startRows": 200,
  "finalRows": 900,
  "polledFrames": 19,
  "framesShowingLoadingHint": 10,
  "hintSample": "正在加载更多…",
  "hintStillPresentAtEnd": false,
  "rowsReachable": "✅ 900 封仍全部可达（分页没回归）"
}
```

19 帧里有 10 帧看得到提示，加载完自动消失，分页无回归。

> 探测用 `requestAnimationFrame` 而不是 `setTimeout`：本地 IPC + SQLite 极快，
> 这个提示可能只存在一两帧，定时器的分辨率会漏掉它 —— 那会得出「没渲染」的错误结论。

### 3.2 把 `App.tsx` 降回 100 行以内（**违背本项目自身规则**）

`AGENTS.md` 粒度限制：React 组件 ≤ 100 行。`App.tsx` **此前是 125 行**，
一直超标，只是没人量过。本轮处理：

| 处理 | 结果 |
| --- | --- |
| `listTitle` / `emptyHint` 两个纯函数抽到 `features/inbox/listLabels.ts` | 它们是视图模型，与组件组装无关 |
| 分页逻辑抽成 `features/inbox/usePagedRows` | 外壳不该知道分页游标怎么算 |
| `App.tsx` | 125 → **93** 行 |
| `MessageList.tsx` | 82 → **94** 行（加了加载提示，仍在限内） |

**教训**：规则写了不等于有人量。`App.tsx` 超标是连续多个任务一点点加上去的，
每个任务单看都「只加了几行」。粒度限制需要**实测行数**来守，不能靠自觉。
